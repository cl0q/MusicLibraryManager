# Phase 12.1: Consistent Path Resolution — organized_path always relative to root - Research

**Researched:** 2026-03-31
**Domain:** Database schema, path handling (backend Rust + Tauri commands, frontend React)
**Confidence:** HIGH

## Summary

Phase 12.1 addresses a critical path consistency issue: `organized_path` must ALWAYS be stored in the database as relative paths (relative to library root), never absolute paths. Currently, the codebase has mostly correct relative path handling in the download pipeline, but there are inconsistencies and potential bugs in:

1. **Test data generation** — sync cache and playlist gen modules hardcode relative paths in test fixtures, but real data may vary
2. **Path resolution edge cases** — reveal_in_file_manager already handles both absolute and relative paths, but this defensive coding suggests uncertainty about what's actually stored
3. **Frontend path usage** — React components pass relative organized_path to reveal_in_file_manager, which correctly joins it with root_path, but there's no validation that organized_path is never absolute
4. **Import module consistency** — generate_organized_path creates relative paths, but doesn't enforce this contract with the database

The discovery gap: **We don't have runtime state inventory** to identify if absolute paths are currently stored in existing databases. This is critical because it determines whether this phase requires data migration (update existing records) or just code auditing (prevent future absolute paths).

**Primary recommendation:** (1) Add comprehensive assertions and conversions to enforce "organized_path is always relative" throughout the codebase, (2) Create audit queries to detect any absolute paths already in production, (3) Implement automated conversion in download/import code to strip library root from any absolute paths before DB storage, (4) Add validation layer in all code paths that write organized_path.

## Current Path Handling Analysis

### 1. Download Pipeline (CORRECT in principle, needs validation)

**File:** `src-tauri/src/download/orchestrator.rs`

- **organize_file_impl()** (lines 642-685): Creates subdirectories under root_dir, returns **absolute path** to final file
- **download_single_track()** (lines 576-610): Collects absolute paths in `BatchResult.downloaded_paths`
- **download command handler** (src-tauri/src/commands/download.rs, lines 120-133): **Correctly strips absolute paths to relative** before storing in DB:
  ```rust
  let absolute = PathBuf::from(file_path);
  let relative_path = absolute
      .strip_prefix(&root_path)
      .map(|p| p.to_string_lossy().to_string())
      .unwrap_or_else(|_| file_path.clone());  // ⚠️ Fallback: if strip fails, use original (could be absolute!)
  ```

**Issue:** The `unwrap_or_else` fallback could theoretically store an absolute path if `strip_prefix` fails. This is a safety bug.

**Risk:** HIGH — if library is moved/remounted, organized_path becomes invalid.

### 2. File Reveal (Defensive but correct)

**File:** `src-tauri/src/commands/library_config.rs` (lines 242-342)

```rust
let resolve = |p: &str| -> PathBuf {
    if Path::new(p).is_absolute() {
        PathBuf::from(p)
    } else if let Some(ref root) = config.root_path {
        root.join(p)
    } else {
        PathBuf::from(p)
    }
};
```

**Observation:** This code handles both absolute and relative paths. The fact that this defensive coding exists suggests someone anticipated the possibility of absolute paths in organized_path. This is a code smell — organized_path should NEVER be absolute, so this logic is unnecessary complexity.

## Architecture Patterns

### Pattern: Path Validation at Write Time

**What:** Every code path that writes organized_path should validate (or assert) that the path is relative, not absolute.

**When to use:** Before executing `INSERT` or `UPDATE` on tracks table.

**Example (Rust):**
```rust
fn validate_relative_path(path: &str) -> Result<(), String> {
    if Path::new(path).is_absolute() {
        return Err(format!("organized_path must be relative, got: {}", path));
    }
    Ok(())
}

// Before storing:
validate_relative_path(&organized_path)?;
conn.execute(
    "UPDATE tracks SET organized_path = ? WHERE id = ?",
    params![organized_path, track_id],
)?;
```

### Pattern: Path Normalization at Read Time

**What:** When code receives a path that might be absolute, normalize it to relative by stripping library root.

**When to use:** In download handlers, import handlers, or any external data source.

**Example (Rust):**
```rust
fn normalize_to_relative(path: &PathBuf, root: &PathBuf) -> Result<String> {
    root.canonicalize()?;  // Resolve symlinks
    let canonical_path = path.canonicalize()?;
    let relative = canonical_path.strip_prefix(root)?;
    Ok(relative.to_string_lossy().to_string())
}
```

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Path portability | Custom path joining logic | `std::path::{Path, PathBuf}` | Handles OS differences (/, \), symlinks, .. resolution |
| Path canonicalization | String-based path comparison | `Path::canonicalize()` | Resolves symlinks, normalizes separators, handles platform quirks |
| Relative path generation | String manipulation (split, replace) | `Path::strip_prefix()` | Correctly handles edge cases, returns error if not a prefix |
| Path validation | Regex or string checks | `Path::is_absolute()` or `is_relative()` | Correct for all platforms |

**Key insight:** Rust's `std::path` module exists exactly to solve these problems. Using it consistently avoids the entire class of path bugs.

## Common Pitfalls

### Pitfall 1: Defensive Path Resolution Masking Bugs

**What goes wrong:** Code that accepts both absolute and relative paths (like reveal_in_file_manager's `resolve()` function) makes it impossible to catch bugs where absolute paths are stored.

**Why it happens:** Someone encountered or anticipated an absolute path in organized_path and added defensive code to handle it. This hides the root cause rather than fixing it.

**How to avoid:**
- Fail loudly if absolute paths are encountered in production code
- Use assertions (`assert!(!path.is_absolute())`) during development
- Add explicit error handling for the "relative expected" case
- Remove defensive code that handles absolute paths in display/reveal logic

**Warning signs:** Comments like "// Handle both absolute and relative" in read-side code.

### Pitfall 2: Path Stripping Fallback

**What goes wrong:** Code like `path.strip_prefix(root).unwrap_or_else(|_| original_path.clone())` silently falls back to storing an absolute path if the strip fails.

**Why it happens:** Pessimistic error handling — "if we can't make it relative, just store what we have."

**How to avoid:**
- Use `.map_err()` to convert strip_prefix failure to a named error
- Log the failure loudly (log::error!)
- Return Err and let the download fail rather than silently storing bad data
- Add test case that specifically verifies strip_prefix succeeds

**Warning signs:** `unwrap_or_else`, `unwrap_or`, or `.ok()` around strip_prefix results.

### Pitfall 3: Test Fixtures vs. Real Code Divergence

**What goes wrong:** Test fixtures hardcode relative paths (correct), but real code paths don't enforce this contract. Tests pass but production fails.

**Why it happens:** Tests are isolated and deterministic; real code has edge cases (symlinks, mount points, permission issues, concurrent access).

**How to avoid:**
- Add property-based tests that verify `organized_path` is never absolute for ANY generated metadata
- Use the same generation logic in tests and production (don't duplicate)
- Add integration tests that actually join root_path + organized_path and verify the file exists

**Warning signs:** Hand-written test paths that don't use the same generation function as production code.

### Pitfall 4: Forgotten Fallback Paths

**What goes wrong:** Code handles the happy path (relative path) but there's an older code path that stores absolute paths, left over from before the Phase 8 decision.

**Why it happens:** Refactoring is incomplete; old import methods, old download handlers, or legacy fields still exist.

**How to avoid:**
- Audit all code paths that write to organized_path (grep for UPDATE/INSERT)
- Search for `original_path` usage in display/file operations — if you're using original_path as a fallback instead of organized_path, something is wrong
- Code review checklist: "Does this code path validate that organized_path is relative?"

**Warning signs:** `original_path` being used in reveal/file operations instead of `organized_path`, `unwrap_or` defaults to original_path.

## Code Examples

### Validation Pattern (To Add)

```rust
// In src-tauri/src/database/tracks.rs
/// Ensure a path is relative to library root.
/// Fails loudly if absolute path is provided.
fn validate_organized_path(path: &str) -> Result<(), String> {
    if Path::new(path).is_absolute() {
        return Err(format!(
            "organized_path must be relative to library root, not absolute. Got: {}",
            path
        ));
    }
    if path.contains("..") {
        return Err(format!(
            "organized_path must not contain '..', got: {}",
            path
        ));
    }
    Ok(())
}

pub fn update_download_status(
    conn: &Connection,
    track_id: i64,
    organized_path: &str,
    absolute_path: &str,
) -> rusqlite::Result<()> {
    // NEW: Validate before storing
    validate_organized_path(organized_path)
        .map_err(|e| rusqlite::Error::InvalidParameterName(e))?;

    let timestamp = chrono::Utc::now().to_rfc3339();
    let (format, bitrate) = detect_file_format_bitrate(absolute_path);

    conn.execute(
        "UPDATE tracks SET download_status = ?, organized_path = ?, format = ?, bitrate = ?, date_added = ? WHERE id = ?",
        rusqlite::params![timestamp, organized_path, format, bitrate, timestamp, track_id],
    )?;

    Ok(())
}
```

// In src-tauri/src/commands/download.rs
let root_path = PathBuf::from(&root_dir);

for (track_id, file_path) in &result.downloaded_paths {
    let absolute = PathBuf::from(file_path);

    // NEW: Normalize to relative, fail if outside root

    tracks::update_download_status(&db_conn, *track_id, &relative_path, file_path)?;
    log::info!("Updated download_status and organized_path for track {} -> {}", track_id, relative_path);
}

# Phase 11.1: Functional & E2E Test Harness - Context

**Gathered:** 2026-03-22
**Status:** Ready for planning

<domain>
## Phase Boundary

Build a test infrastructure that catches regressions across the Rust backend and React frontend. Backend integration tests exercise full command flows (handler -> database -> filesystem). Frontend component tests verify key components render correctly with mock data. No browser-based E2E — backend integration tests are the workhorse.

</domain>

<decisions>
## Implementation Decisions

### Test layers & scope
- Primary goal: regression safety net (not requirement verification)
- Backend: integration tests covering full Rust command flows with real SQLite
- Frontend: component rendering tests with vitest (verify components render correctly with mock data)
- No browser-based E2E tests — Tauri WebDriver/Playwright excluded (brittle, slow)

### Backend integration test priorities
- Download pipeline: remote track -> DAB/YT download -> transcode -> organize -> DB update
- Import local files: scan directory -> extract metadata -> detect duplicates -> insert DB
- Library/Remote filtering: organized_path IS NOT NULL vs IS NULL queries return correct tracks
- Sync to device: select tracks -> transcode -> copy to device path -> generate M3U8

### Backend test organization
- Integration tests in `src-tauri/tests/` directory (Cargo convention)
- Separated from unit tests: `cargo test` runs unit tests, `cargo test --test '*'` runs integration tests
- Shared test fixtures and helpers in test utility modules

### API mocking strategy
- Record/replay JSON fixtures for external APIs (DAB, SoundCloud, Spotify)
- Capture real API responses once, replay from fixture files in tests
- Deterministic, no network dependency, fast execution
- Fix existing failing DAB test (test_search_not_found — 401 auth error) by converting to fixture-based

### Audio test data
- Tiny generated fixture files (1-second silence) in FLAC, AAC, MP3 formats
- Committed to repo in a test fixtures directory
- Small, deterministic, no copyright issues
- Covers real codec/format edge cases (unlike pure mocking)

### Database strategy
- In-memory SQLite (`:memory:`) with schema migrations applied
- Existing `get_memory_connection()` pattern already used in some tests
- Fast, isolated, no cleanup needed

### Frontend test approach
- Vitest as test runner (standard for Vite-based projects)
- Mock `@tauri-apps/api` invoke() to return canned responses
- Key components to test: LibraryTable, DownloadProgress, MoreInfoPanel, RowContextMenu
- Component rendering verification, not interaction testing

### Runner & CI
- Local only — no CI pipeline for now
- Separate commands: `cargo test` (Rust) and `npm test` (frontend)
- Integration tests separated: `cargo test --test '*'` for integration, plain `cargo test` for unit tests

### Claude's Discretion
- Exact test fixture file structure and naming conventions
- Vitest configuration details (jsdom vs happy-dom, etc.)
- Test helper module structure in `src-tauri/tests/`
- Which specific component props/states to test in frontend

</decisions>

## Existing Code Insights

### Reusable Assets
- `get_memory_connection()` — Existing in-memory SQLite setup used in 342+ unit tests
- `tempfile` crate — Already a dev-dependency, used for temp directories in tests
- 58 Rust source files with `#[cfg(test)]` modules — Established unit test patterns throughout codebase

### Established Patterns
- Unit tests use `#[cfg(test)] mod tests` inline in each module
- Database tests create in-memory connections with schema migrations
- Async tests use `#[tokio::test]` for async runtime
- Download clients (DAB, SoundCloud, YouTube) are struct-based with methods, not trait-based

### Integration Points
- Command handlers in `src/commands/*.rs` — Entry points for integration tests
- Database schema in `src/database/schema.rs` — Schema migrations needed for test DB setup
- `src/download/orchestrator.rs` — Download flow orchestration (most complex integration path)
- `ui/src/utils/tauri-commands.ts` — All Tauri invoke() calls centralized here (mock target for frontend tests)

</code_context>

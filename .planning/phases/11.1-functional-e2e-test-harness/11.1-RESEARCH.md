# Phase 11.1: Functional & E2E Test Harness - Research

**Researched:** 2026-03-22
**Domain:** Tauri v2 application testing (Rust backend + React frontend)
**Confidence:** HIGH

## Summary

This phase builds a regression test harness for the download pipeline and library management components. The strategy divides testing cleanly: Rust integration tests exercise full command flows with real SQLite databases, while React component tests verify rendering with mocked Tauri invocations. No browser-based E2E tests (WebDriver/Playwright) — the backend integration tests are the workhorse for catching regressions across the system.

The project already has 58 modules with inline unit tests (~342 passing tests) and established patterns (`get_memory_connection()`, in-memory SQLite, `#[cfg(test)]` modules). Integration tests will extend this infrastructure into a `tests/` directory using Cargo's standard integration test layout. Frontend tests will use Vitest (Vite-based runner) with `@tauri-apps/api/mocks` to intercept IPC calls.

**Primary recommendation:** Build test infrastructure incrementally: (1) Convert failing DAB test to JSON fixtures, (2) Create integration test framework in `tests/` with shared helpers, (3) Add frontend component tests with mocked Tauri, (4) Map requirements to test cases, (5) Document test coverage baseline.

### Pattern 1: Rust Integration Tests with In-Memory SQLite

**What:** Integration tests live in `tests/` directory (not inline `#[cfg(test)]` modules). Each file is a separate crate that imports the library and tests public APIs. Tests use `get_memory_connection()` to set up isolated databases.

**When to use:** Testing end-to-end command flows: handler → business logic → database mutations → filesystem operations.

**Example:**
```rust
// tests/download_pipeline_test.rs
// Source: Rust By Example integration testing pattern
use music_library_manager::database::get_memory_connection;
use music_library_manager::download::orchestrator::DownloadOrchestrator;
use std::path::PathBuf;
use tempfile::TempDir;

#[tokio::test]
async fn test_download_pipeline_dab_success() {
    // Setup
    let mut conn = get_memory_connection().unwrap();
    let temp_dir = TempDir::new().unwrap();
    let download_path = temp_dir.path().join("downloads");
    let transcode_path = temp_dir.path().join("transcoded");
    let library_path = temp_dir.path().join("library");

    std::fs::create_dir_all(&download_path).unwrap();
    std::fs::create_dir_all(&transcode_path).unwrap();
    std::fs::create_dir_all(&library_path).unwrap();

    // Insert test track into remote (organized_path IS NULL)
    conn.execute(
        "INSERT INTO tracks (artist, album_artist, album, title, format, original_path)
         VALUES ('Test Artist', 'Test Artist', 'Test Album', 'Test Song', 'stream', 'remote://test')",
        [],
    ).unwrap();
    let track_id: i64 = conn.query_row("SELECT last_insert_rowid()", [], |row| row.get(0)).unwrap();

    // Create orchestrator and download (mocked via fixture JSON)
    let mut orchestrator = DownloadOrchestrator::new(
        download_path.clone(),
        transcode_path.clone(),
        Some(library_path.clone()),
    ).unwrap();

    // Mock progress callback to verify state changes
    let mut progress_events = Vec::new();
    let progress_callback: Box<dyn Fn(TrackProgress) + Send + Sync> = Box::new(|tp| {
        progress_events.push((tp.track_id, tp.status));
    });

    // Execute download (will use fixture JSON for DAB response)
    let result = orchestrator.download_batch(vec![request], progress_callback).await.unwrap();

    // Assert results
    assert_eq!(result.succeeded, 1);
    assert_eq!(result.failed, 0);

    // Verify database was updated
    let updated_track: (Option<String>, String) = conn.query_row(
        "SELECT organized_path, format FROM tracks WHERE id = ?",
        [track_id],
        |row| Ok((row.get(0)?, row.get(1)?)),
    ).unwrap();

    assert!(updated_track.0.is_some(), "organized_path should be set after download");
    assert_eq!(updated_track.1, "aac", "Format should be updated to transcoded format");
}
```

### Pattern 2: API Fixture-Based Mocking (JSON Record/Replay)

**What:** External API responses (DAB, SoundCloud, YouTube) are captured as JSON files and loaded by tests instead of making real HTTP calls.

**When to use:** Testing download flows that depend on external API responses. First instance: fix `test_search_not_found` 401 error by using fixture instead of live API.

**Example:**
```rust
// tests/common/api_mocks.rs
// Source: Project pattern — manual JSON fixture management
pub struct MockDabClient {
    fixture_dir: PathBuf,
}

impl MockDabClient {
    pub fn new_with_fixture(fixture_name: &str) -> Result<Self> {
        let fixture_path = PathBuf::from("tests/common/fixtures/dab")
            .join(format!("{}.json", fixture_name));

        // Load JSON fixture
        let fixture_json = std::fs::read_to_string(fixture_path)?;
        let fixture: serde_json::Value = serde_json::from_str(&fixture_json)?;

        Ok(Self { fixture_dir: PathBuf::from("tests/common/fixtures/dab") })
    }

    pub async fn search_and_download(
        &self,
        track_id: &str,
        artist: &str,
        title: &str,
        output_path: &PathBuf,
    ) -> Result<DownloadResult> {
        // Return fixture response instead of HTTP call
        // Fixture contains: { "status": "success", "stream_url": "...", "file_size": ... }
        // or: { "status": "not_found" }
        // or: { "status": "error", "code": 401, "message": "Auth failed" }

        let fixture = self.load_fixture()?;
        match fixture["status"].as_str() {
            Some("success") => {
                // Copy test audio file to output_path
                let test_audio = self.fixture_dir.join("test_audio.flac");
                std::fs::copy(&test_audio, output_path)?;
                Ok(DownloadResult::Success { file_size: ... })
            },
            Some("not_found") => Ok(DownloadResult::NotFound),
            Some("error") => Err(anyhow::anyhow!("API error: {}", fixture["message"])),
            _ => Err(anyhow::anyhow!("Invalid fixture format")),
        }
    }
}
```

Fixture file: `tests/common/fixtures/dab/search_not_found.json`
```json
{
  "status": "not_found",
  "query": "xyznonexistent",
  "message": "No results found for query"
}
```

### Pattern 3: Frontend Component Tests with Tauri Mocking

**What:** React components render in isolation with Tauri API calls mocked via `@tauri-apps/api/mocks`. Tests verify that components render correctly with given props and that they invoke the correct backend commands.

**When to use:** Testing rendering logic and component behavior without needing the Rust backend or browser.

**Example:**
```typescript
// ui/tests/components/LibraryTable.test.tsx
// Source: Tauri mocking pattern from @tauri-apps/api/mocks v2.10.1
import { describe, it, expect, beforeEach, afterEach, vi } from 'vitest';
import { render, screen } from '@testing-library/react';
import { mockIPC, mockWindows, clearMocks } from '@tauri-apps/api/mocks';
import LibraryTable from '../../src/components/LibraryTable/LibraryTable';
import type { Track } from '../../src/types/library';

describe('LibraryTable', () => {
  beforeEach(() => {
    mockIPC((cmd, args) => {
      // Intercept any Tauri invoke calls
      if (cmd === 'get_library_config') {
        return { root_path: '/mock/library' };
      }
      return null;
    });
    mockWindows('main');
  });

  afterEach(() => {
    clearMocks();
  });

  it('renders library tracks with correct columns', () => {
    const mockTracks: Track[] = [
      {
        id: 1,
        metadata: { title: 'Test Song', artist: 'Test Artist', album: 'Test Album' },
        organized_path: '/mock/library/T/Test Artist/Test Album/Test Song.aac',
        format: 'aac',
        bitrate: 248,
      },
    ];

    render(<LibraryTable tracks={mockTracks} />);

    // Verify rendering
    expect(screen.getByText('Test Song')).toBeInTheDocument();
    expect(screen.getByText('Test Artist')).toBeInTheDocument();
  });

  it('shows context menu on right-click', () => {
    const mockTracks: Track[] = [{ /* ... */ }];
    const { container } = render(<LibraryTable tracks={mockTracks} />);

    const row = container.querySelector('tbody tr');
    // Right-click simulation
    fireEvent.contextMenu(row!);

    // Verify context menu appears
    expect(screen.getByText('Download')).toBeInTheDocument();
  });
});
```

### Anti-Patterns to Avoid

- **Testing implementation details:** Don't test "invoke was called with X" — test that the correct result appears in the UI or database
- **Brittle mocks:** Don't mock every function call — mock at boundaries (Tauri API, external HTTP)
- **Mixing test concerns:** Don't test download logic inside a component test; use integration tests for that
- **Skipping fixture setup:** Don't use live API calls in tests; always capture responses as fixtures first
- **Ignoring database isolation:** Don't reuse connection state between tests; always use fresh `get_memory_connection()`
- **Browser-based E2E:** Don't use Playwright/WebDriver for regression testing (slow, brittle); reserve for critical user flows

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| HTTP mocking for DAB/YouTube | Custom HTTP server or request interception | JSON fixtures + manual loading | Simpler than HTTP mocking library, user decision respects this, deterministic |
| Database setup for tests | Custom schema initialization script | `get_memory_connection()` + migrations | Already exists in codebase, proven pattern, no cleanup needed |
| React component rendering verification | Custom render logic | @testing-library/react + Vitest | Industry standard, better debugging output, semantic queries |
| Tauri IPC mocking | Custom window mock objects | @tauri-apps/api/mocks | Official Tauri library, designed for v2, handles clearMocks cleanup |
| Test data builders | Ad-hoc SQL inserts in every test | Shared helpers in `tests/common/fixtures.rs` | DRY principle, reduces test boilerplate, easier to maintain |

**Key insight:** The project already has 342 passing unit tests with established patterns. Integration tests should extend these patterns (in-memory SQLite, reusable helpers) rather than building new infrastructure.

## Common Pitfalls

### Pitfall 1: Live API Calls During Tests
**What goes wrong:** Test calls real DAB/SoundCloud API, fails with 401, 429, or network timeout. This is why `test_search_not_found` is currently broken.

**Why it happens:** Forgetting to mock external dependencies; developer assumes API will be available during test run.

**How to avoid:** (1) All HTTP calls go through mocked clients by default, (2) Fixtures captured once and checked into git, (3) In tests, patch HTTP client to return fixture responses, (4) Add test markers (`#[test]` with `ignore` attribute) for tests that require network.

**Warning signs:** Test passes locally but fails in CI; test fails with 4xx/5xx errors from external service; test is slow (> 5 seconds).

### Pitfall 2: Database State Leakage Between Tests
**What goes wrong:** Test A inserts a track, test B reads it, tests fail in different orders. Example: two tests both expect "no tracks in database" but one runs after the other.

**Why it happens:** Using shared file-based SQLite or forgetting to clear state between tests.

**How to avoid:** Always use `get_memory_connection()` (creates fresh isolated database), never reuse connections across tests, always drop/cleanup temp directories in tests.

**Warning signs:** Test passes in isolation but fails when run with `cargo test --` (all tests), random ordering failures, cleanup code in test teardown.

### Pitfall 3: Async Test Timeouts
**What goes wrong:** Integration test hangs or times out waiting for async operation that never completes.

**Why it happens:** Forgetting `#[tokio::test]` attribute, or async callback never called because mocked dependency returns wrong type.

**How to avoid:** (1) Mark async tests with `#[tokio::test]`, not `#[test]`, (2) Add timeout attributes for long-running tests, (3) Mock callbacks to verify they're invoked, (4) Test both success and error paths.

**Warning signs:** Test never completes; cargo test hangs; panic about "runtime" not found.

### Pitfall 4: Incomplete Database Schema in Memory Tests
**What goes wrong:** Test creates in-memory connection but foreign key constraint fails; schema version doesn't match; migration scripts don't run.

**Why it happens:** `get_memory_connection()` initializes schema but developer adds new table/column without running migrations.

**How to avoid:** Always call `get_memory_connection()` (it runs `initialize_schema()`), which applies all migrations up to current version. If tests fail with "table not found", check that CURRENT_SCHEMA_VERSION matches codebase schema files.

**Warning signs:** "no such table" error in test; foreign key constraint violation; database locked error.

### Pitfall 5: Mocking the Wrong Boundary
**What goes wrong:** Test mocks internal function, test passes, but integration test of full flow fails because real function had different behavior.

**Why it happens:** Developer mocks a private helper function instead of the external boundary (HTTP client, file I/O).

**How to avoid:** Mock only at external boundaries: HTTP clients, filesystem operations, Tauri IPC. Don't mock internal business logic. Test the full flow end-to-end with mocked externals.

**Warning signs:** Unit test passes but integration test fails; test setup more complex than actual test; test setup requires mocking more than 2 things.

## State of the Art

| Old Approach | Current Approach | When Changed | Impact |
|--------------|------------------|--------------|--------|
| No organized test infrastructure | Integration tests in `tests/` directory with shared fixtures | Phase 11.1 | Enables regression safety for complex pipelines |
| 342 unit tests inline in modules | 342 inline unit tests + new integration layer | Phase 11.1 | Separates concern: unit = module behavior, integration = end-to-end flows |
| Live API calls in tests (failing DAB test) | JSON fixtures with manual record/replay | Phase 11.1 | Deterministic, fast, no network dependency |
| No frontend component tests | Vitest + @testing-library/react with Tauri mocking | Phase 11.1 | Catch rendering regressions without browser |
| Jest (if any) | Vitest (Vite-native, 10x faster) | Phase 11.1 | ESM-first, lower overhead, native Vite integration |

**Deprecated/outdated:**
- Browser-based E2E (Playwright/WebDriver) for basic regression testing: **Deprecated in favor of integration tests** — too slow (30+ seconds per test), brittle (UI changes break tests), flaky (timing issues). Reserve WebDriver for critical user journeys only.
- Manual HTTP server setup for testing: **Replaced by JSON fixtures** — simpler, deterministic, no network, easier to review.

## Open Questions

1. **Vitest configuration (happy-dom vs jsdom):**
   - What we know: happy-dom is lighter, jsdom is more complete. Component tests don't need full browser simulation.
   - What's unclear: Performance impact on test suite, whether any components use jsdom-specific APIs.
   - Recommendation: Start with happy-dom (faster), fall back to jsdom if tests fail. Document choice in vitest.config.ts.

2. **Audio fixture generation:**
   - What we know: Tests need 1-second silence files in FLAC/AAC/MP3 formats.
   - What's unclear: Easiest way to generate these deterministically (ffmpeg command vs. binary blob).
   - Recommendation: Generate once with `ffmpeg -f lavfi -i anullsrc=r=44100:cl=mono -t 1 silence_1sec.flac` and check into repo. Commit binary files with `.gitattributes` to prevent line-ending issues.

3. **Test coverage expectations:**
   - What we know: Phase wants regression safety, not requirement verification.
   - What's unclear: Acceptable coverage threshold (80%? 60%? lines vs. branches?).
   - Recommendation: No formal threshold; focus on high-risk flows (download pipeline, library filtering). Aim for "any code change triggers a test failure" — high confidence that tests catch regressions.
